# Dashboard

The dashboard is where you watch and steer delivery: the board, each item's story, the agents, reports and the operator. It is served by `conveyor serve` (default `http://127.0.0.1:7788`) and needs a signed-in account (`conveyor init` creates the first).

The shared header is followed by the view navigation: **Board**, **Team**, **Reports**, and **Operator**. **Label problems** appears when enrolled issues have missing, unknown, or conflicting stage labels (and remains available on its empty page). The Board alone shows **The line** and its **Needs you** panel. The line folds with the arrow beside its name: it is open on wide screens and closed on phones until you choose, and the choice is remembered in the browser; when questions or stopped items need a person, every view links to that panel with the same count. The account menu contains Profile, About Conveyor, Sign out, and Accounts for administrators; Notifications remains in the header.

## Screenshots

The screenshots below are generated by `bun run docs:screenshots` from isolated demo data whenever the dashboard layout changes. In a fresh checkout, run `bun install --frozen-lockfile` and `bunx playwright install chromium` once, then run the command from the repository root. It starts Conveyor with seeded demo items and captures each view at a fixed 1440×1024 viewport. If you change the dashboard layout, regenerate and commit the screenshots in the same pull request; PR Check runs the command twice and verifies pixel-identical images.

The board shows backlog, configured stages, completed work, active runner capacity, dependency/child relationships, warnings, questions, and per-stage usage (tokens in and out, plus the dollar amount when the harness reports one; subscription harnesses do not). Issue dialogs separate four concerns:

- **Summary** — current state, relationships, criteria, labels, token usage (and cost when known), and duration.
- **Conversation** — concise owner and agent handoff messages that survive future runs.
- **Journey** — stage transitions, corrections, stops, and their reasons.
- **Technical logs** — paginated raw run events for debugging.

Parent items and their children appear as family rows. The stations stay across the top; each open parent gets a row whose header shows its number and title, one square per child (solid green done, solid red stopped, outlined green running, outlined amber waiting), `done/total`, the parent's own stop when it has one, and **Details** for the parent's dialog. The children are cards in their stations within that row, and the row's Done column lists the parts already finished. Items without a parent share the bottom row, where the backlog can be reordered. The arrow folds a row to its header, and each browser remembers which rows are folded. A finished family shows only its parent, as one card in Done. On a phone, a family row lists its cards in stage order with the stage on each card, while the bottom row swipes between stations.

Dependencies are chips on the card that waits: **Waiting on #245 · Blocked** turns red when the blocker itself is stopped, so a wait that will not clear on its own stands out; finished dependencies drop off. An item that others wait on shows **Blocks N**, and a family row shows it when items wait on the parent. Tapping any of these chips traces the chain both ways across the rows, including through parents (whatever waits on a parent is held up by its unfinished parts): the traced item is outlined, what holds it up is dashed red and labelled, what waits on it is dashed blue and labelled, everything else dims, and a folded row that holds part of the chain opens. The banner names the direct links and counts the whole chain; **Show everything**, the chip again, or Escape clears it.

### Todos

The implementer keeps a working todo list (`todo.set`, `todo.update`). When the implementation stage passes its exit gate and the item advances, Conveyor closes the list out: every `pending` or `in_progress` entry becomes `skipped` with a system note, and `done` entries are untouched. The skipped status is Conveyor-owned; agents cannot set or change it. If the item returns to implementation (a review finding or a failed gate), skipped entries remain as history and the implementer adds new todos under new ids. Cards show todo progress (`finished/total`, where finished counts done and skipped) only while the item is in the implementation stage; cards in later stages and in done show none. The item details always keep the full list, with skipped entries labelled and the skipped count shown.

## Keyboard and assistive technology

Every view has its own page title, and a **Skip to content** link is the first tab stop. Issue and agent cards open from the button in their title with Enter or Space; inside an item, the arrow keys, Home and End move between Summary, Conversation, Journey and Technical logs, and Escape closes it and returns to the card. Following a link keeps keyboard focus on that link when the next view has it, and otherwise moves it to the start of the content. Live updates keep the focused control and anything half-entered, and wait while you are typing or have a header menu open.

A live update does not reload the page. The event stream (`/events/dashboard`) says only that something changed; the browser then asks for the page it is showing with an `x-conveyor-cards` header listing the revision of every card it holds (`data-card-revision`, a digest of everything the card shows). The server answers with the same page, in which each card the browser already holds is an empty placeholder (`data-keep`), and the browser patches the difference into the page in place. A card that did not change is never removed from the page, so what you are reading stays where it is; a card that changed, moved to another stage, appeared or disappeared is the only thing touched. An update waits while a finger is on the screen or a scroll is still coasting, and the request needs the same session as the page. If the page no longer holds a card the answer kept, the browser asks again for every card. Navigation between views loads a whole page as before.

## Repositories

**Repositories** (`/repositories`) lists every configured repository with its id, address, health, and current work. The Board does not list repositories, but when one cannot sync, a notice above the line names it, gives the error, and links to its page, since its items may be out of date. Select one to open `/repositories/<id>`, which provides its current delivery status, recent work, and **Setup**. Setup shows the provider configuration to every signed-in user, but only superusers see the local folder and agent egress hosts.

![Configured repositories](screenshots/repositories.png)

![Repository detail and setup](screenshots/repository.png)

**Reports** (`/reports`, drill into one repository with `/reports/<repository>`, filter with `?period=7d|30d|90d|12m`, all time by default) show delivery, usage and time: items delivered and in progress, runs (and how many did not succeed), tokens and their cached share, agent time, and per delivered item the average tokens, runs, lead time (enrolled to done), returns and first-pass rate. It breaks an item's lead time into agents working, waiting on CI and checks, waiting for you (stopped) and queued, and shows tokens and agent time per stage, per repository and per month. A repository's page lists its items with the same figures, each linking to the item. An item counts as delivered when it finishes its last stage; done items imported without that record are left out and counted in a note.

![Reports](screenshots/reports.png)

The optional steering agent is intentionally quieter than the technical log. Only explicit MCP progress and the final report are shown; commands, tool calls, raw output, and private reasoning are not rendered.

## Browser push notifications

Serve the dashboard over HTTPS (a reverse proxy can provide TLS), then configure `web.push` with a VAPID public/private key pair and an `https:` or `mailto:` contact subject. Generate a pair with `bunx web-push generate-vapid-keys`, and keep the private key in `secrets.yaml`. Restart Conveyor after changing the keys. Without all three values, the dashboard still works and shows push as unavailable.

Signed-in users can opt in separately to new questions, newly stopped issues, and issues reaching done from **Notifications** in the dashboard. Every category starts off. Enabling a category asks the browser for notification permission and registers that browser; users can turn categories off at any time, and turning all of them off or signing out removes that browser's server-side subscription. Push requires HTTPS, service workers, the Push API, and the Notifications API. Browsers that do not implement those APIs, or that restrict push for installed web apps, cannot receive alerts; the settings page reports unsupported or denied permission states.
